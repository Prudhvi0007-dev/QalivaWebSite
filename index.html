Context Studio

Ask your files anything.

Context Studio · Architecture

One question, four stages.

1Bring it in

Drop it in. It's searchable in seconds.

Specs, decks, recordings, websites and Jira stories land in one workspace. The full read carries on in the background.

  • Upload returns at once. Extraction, chunking and indexing run in the background, so a file is searchable within seconds.
  • PDFs up to 1,000 pages, with running headers, footers and page numbers removed before chunking.
  • Scanned pages with no text layer are read by gemma4:e4b.
  • Word and PowerPoint, including pictures inside them, which can be found by what they show.
  • Audio and video transcribed by Whisper into passages of about 45 seconds, each with its start and end time.
  • Websites, including dashboards built by JavaScript, and YouTube transcripts by chapter.
  • Jira and Confluence connectors: one Markdown file per sync, one section per issue or page. Emails, card numbers, Aadhaar, PAN and other personal data are masked before indexing.
  • Uploading a file with the same name replaces the older version once the new one is indexed.

2Index

Every passage remembers where it came from.

Files are split inside their own sections and labelled with the section and pages. Tables stay as rows.

  • First pass: 850-character chunks with a sentence of overlap, so search works straight away.
  • Section-aware pass: once the section tree exists (PDF bookmarks or layout, Markdown headings), the file is re-chunked inside section boundaries. Every chunk starts with § Path › Section (p. X–Y).
  • Tables: one line per row, every value named by its column, and every row indexed.
  • Vectors: EmbeddingGemma 2 at 512 dimensions, with the section path as the title. Pictures, video and audio share the same vector space.
  • Also built: a keyword index (full-text and TF-IDF), the section tree for Deep search, and graph facts.

3Find

Several searches run at once and agree on the evidence.

Keyword, meaning, pictures, tables and sections each put forward passages. They're merged by rank, and Laya checks the winners for injected instructions.

  • One Laya question pack decides the route, the guard and the answer shape while the question is being embedded.
  • Lanes in parallel: keyword (full-text and TF-IDF), meaning (EmbeddingGemma 2), pictures and recordings, and graph lookup.
  • Table questions: exact lanes answer lookups, counts, ranks and filters with no model. Harder ones become one read-only SELECT that gemma4:e4b writes against an in-memory copy (2 s limit, 200 rows).
  • Merged with reciprocal rank fusion, so a passage several lanes agree on rises to the top.
  • Deep search (opt-in): Gemma reads the table of contents first, which lifted the top hit on long PDFs for about 5 seconds more.
  • Laya guard checks the final passages for injected instructions. Each passage is labelled with its section and pages.

4Answer

An answer you can check, sentence by sentence.

gemma4:e4b writes the answer. Code then matches every sentence to the passage behind it. Select a number to read the exact text it came from.

  • gemma4:e4b answers, streamed from Ollama. It isn't asked to cite, because a 4B model cites unreliably.
  • Code checks every sentence against the passages: word overlap weighted by rarity, light stemming, and every number must match. About 15 ms for a 12-sentence answer.
  • Three verdicts: supported, partly supported (it says what's missing), or not found, marked ?.
  • Opening a number shows the passage with the supporting sentences highlighted, and jumps to that page in the file.
  • In the evals: citations on 28 of 28 answers in both suites, no ? on any of the 53 right answers, and 24 of 24 unanswerable questions declined.

Control a Browser

Control a Browser

Give it a goal.
It works the page one checked step at a time.

Control a Browser · Architecture

A loop that checks every step.

1Observe

It reads the page the way a tester would.

An accessibility snapshot plus a screenshot. Every control gets a number in reading order, drawn on QALIVA's own copy, never on the page.

  • Snapshot with boxes, a screenshot at CSS scale, and a fixed page probe: secret fields, captcha frames, scroll position and focus.
  • Numbers in reading order, drawn on QALIVA's copy of the screenshot. Nothing is added to the page.
  • Icon-only controls are named from their test id, class, title or link, for example a cart icon becomes link, no label (looks like "shopping cart").
  • A blank page is waited on, 2 seconds at a time for up to 8, and read again before anything is decided.
  • Its own browser: a separate Playwright MCP instance and Chrome profile, with Chrome's sandbox kept on.

2Decide

One action, then code checks it.

gemma4:e4b answers with a single action and a short reason. Code confirms the target exists and that every typed value has a source, then looks at the page once more before acting.

  • One action per turn: click, type, choose, key, scroll, hover, find, back, open, wait, tab, dialog, ask, done or stuck, with a reason of at most 12 words.
  • A typed value must have a source: the goal, your answers, notes or the page. A value with no source, refused twice, becomes a question to you.
  • An unusable answer gets one corrected try. A control you said no to is refused in code.
  • Bind: a fresh snapshot just before acting. The decision is dropped if the address changed, a dialog opened, or the target moved.
  • Planning: every plan covers every part of the goal. It re-plans after 12 actions on one step or when the same screen keeps coming back.

3Gate

Anything that commits waits for your yes.

Pauses are rules in code, and the model can't switch them off. Even a button that only says "Continue" stops when it would send your details.

  • Secret: passwords, one-time codes and card fields are typed by you. A card number is never typed.
  • Commit: commit words (pay, send, delete, submit…), a POST form, a checkout step that shows a total, or a button that sends a form asking for your name, email, phone or address.
  • Scope and links: leaving the task's sites, or opening an address that came from page content, asks first.
  • Laya's risk score can only add a pause. Laya Lab measured it ranking commits no better than chance, so it never removes one.
  • Only the QALIVA screen can approve. A page open in the agent's browser can't answer its own pause.

4Act and record

It acts, checks what changed, and keeps a replay.

Each action is one Playwright MCP call. If nothing changed, that tactic isn't offered again. Every step leaves a trace line and a marked screenshot, and a finished run exports scripts you can replay.

  • One MCP call through an allowlist. The model never calls a tool itself, and only four fixed probe scripts ever run in the page.
  • Compare: address, content, layout, scroll, focus, tabs and picture. When nothing changed, the model is told and that tactic is retired for the step.
  • Record: one line in trace.jsonl and a marked step-NNN.jpg per step, plus Playwright's own trace.
  • Exports: replay.spec.ts and test_replay.py, with detours and dead clicks dropped, a pause before approved commits, and secrets left as placeholders.
  • Budgets: 60 actions and 10 minutes per run. Time spent waiting for you doesn't count.

Work mate

Work mate

A Jira story in.
A filed test plan out, after you approve.

Work mate · Architecture

Two stops. Both are yours.

1Pick up

It starts from the story already assigned to you.

Your open stories are listed with where each one stands. Work mate reads the requirement attachments and works out whether the story is web, mobile or API.

  • Your stories: the open issues assigned to the account behind the Jira connector. Its token stays in the secret store.
  • Pick the next story takes the one that has waited longest, testing work first.
  • Read: text, Markdown, CSV, JSON, HTML and PDF attachments. Images and Word files are listed and skipped, and so is any file named like a test plan Work mate filed before.
  • Surfaces: web, mobile and API words in the story, ignoring what it searches for and anything quoted. "Search for iPhone duo" isn't a mobile test.
  • Reading and drafting are read-only. Nothing is written to Jira at this stage.

2Draft and review · stop 1

It drafts the cases, then waits for you.

gemma4:e4b drafts the cases, and anything it can't trace back to the story is dropped. You edit them or ask the mate for changes until you approve.

  • Drafted by gemma4:e4b in JSON mode, in about 20 to 30 seconds on the 16 GB Mac. The model gets the story, the requirement files and your saved preferences.
  • Kept honest: an address or exact phrase that isn't in the story, your preferences, your messages or your edits is dropped, and the mate says which.
  • Ask the mate in plain words ("add a negative case for an expired card"). Each change is a new version, up to 12 are kept, and Undo goes back one.
  • Preferences are standing instructions used for every draft, such as "one negative case per requirement".
  • If the model can't be reached, a rules-based draft takes over and the review panel says so.

3Test

Cases run in a real browser, and each one says what it proved.

After you approve, Work mate files a subtask, moves the story to In Progress and runs each web case through Control a Browser. Its questions wait for you here.

  • Tasks: one subtask per surface, or the one filed before is reused.
  • Each web case becomes a goal for Control a Browser: its steps, the expected result and the exact text to find, plus a note not to buy, pay or sign up unless the goal says so.
  • Its questions wait in Work mate: approve a risky click, type a password, or answer "Is the goal done?". Unanswered for 15 minutes, the case stops.
  • Passed means every step was done and the exact text is on the last page. Ran means not proven, with the reason. Not run means it never reached the browser.
  • Proof per case: the last six step pictures and the last page, with the trace and replay scripts kept in the run folder.

4Check and attach · stop 2

You make the call. Then the plan goes on the story.

Nothing is attached until you've checked the results. Mark a case yourself with a reason, and the plan records both your call and what the run saw.

  • Your call per case: Passed or Failed, with why. The plan shows both, for example Result: passed (marked by Prudhvi: checked the price by hand) and As run: opened.
  • Fix a case (steps, page, searches or exact text) and run it again, or tick several and run them again.
  • Attach to Jira puts {KEY}-test-plan.md on the story and its tasks with a comment. The plan says who approved it, which version and model drafted it, and your calls.
  • Finish without attaching ends the run with nothing written. If Jira is down, the run goes back to Check results.
  • Run tests again reruns the approved cases with no redraft and no model call.

Laya Mobile Lab

Laya Mobile Lab · Architecture

Laya first. Gemma when it isn't sure.

1Bring your app

Install it, and QALIVA takes a first look.

Add a simulator build, an .ipa or an .apk. The first look reads the screen once, lists what can be tapped or typed into, and flags controls with no accessibility label.

  • Add app: recent Xcode simulator builds, an uploaded .zip or .ipa (iOS) or .apk, or a path on the Mac. The bundle id and name come from Info.plist; device-only builds are refused with advice.
  • First look runs after install: it launches the app, reads the hierarchy once, and lists names to Tap, Type into and Check. The iOS status bar is dropped.
  • Login secrets are stored as ${APP_PASSWORD} in an owner-only file. Runs and replays fill them in; saved flows keep only the name.
  • Built-in apps such as Photos are restarted instead of cleared, because iOS doesn't allow clearing their data.
  • Not installed means no run, with a prompt to install again or add the app.

2Plan the run

Your prompt sets the step budget.

The prompt is split into parts, each with a weight. The budget follows from the total, grows when a part finishes, and a run that stops making progress says where it got stuck.

  • Weights: delete, recover and add are 3; go to, scroll, type and toggle are 2; tap, back and verify are 1; launching the app is 0.
  • Budget = 1.5 × total + 4, between 12 and 60. A number you type is a hard limit from 1 to 99.
  • Progress is a part done, a pending target appearing for the first time, or a new screen. The planner sees each part as done, now or to do.
  • Loops (the same action three times, swipes that never reveal the target, bouncing between two screens) are blocked, and QALIVA taps a way out such as Close or Back. After three loops the run stops.
  • No progress for 8 steps stops the run with where it is and what's left: "Done 3 of 7 parts. Next part: …".

3Decide each tap

Laya goes first, but only when it's sure.

Laya answers in milliseconds. Above 0.80 it acts, between 0.60 and 0.80 the model checks it, and below 0.60 gemma4:e4b decides. EmbeddingGemma 2 matches the words you used to the labels on screen.

  • Laya, used zero-shot, at about 190 ms per decision. At 0.80 or more it acts; from 0.60 to 0.80 the model verifies; below 0.60 the model decides.
  • Evidence check: a screen Laya calls a dialog, login, checkout, cart or error needs supporting words on screen, or it becomes UNKNOWN and the step goes to the model.
  • EmbeddingGemma 2 ranking: 0.7 meaning plus 0.3 keyword. A named tap that isn't on screen goes to the closest confident match.
  • First, last, nth: read from the layout's geometry, or from tiles in the screenshot when a grid has no names. The tap is then a percentage point.
  • Measured on a real run: Laya called the Photos viewer a permission dialog. The evidence check turned that into UNKNOWN, and gemma4:e4b made the tap.

4Check and save

It stops when the screen shows the goal, then saves a replay.

The goal check reads the control's state, so a heart that turns filled ends the run and is recorded as an assert. A passing run becomes a Maestro flow that replays with no model at all.

  • Toggle awareness: icon pairs such as heart and heart.fill, label pairs such as Follow and Following, and switch state. Icon evidence beats a static label that never changes.
  • Re-tapping a flipped control is blocked, and a finish that doesn't meet the goal is refused.
